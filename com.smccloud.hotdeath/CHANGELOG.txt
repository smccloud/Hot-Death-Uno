Version 1.4.7                2026-10-01

 - VERSIONING FIXED, and this is the first release under the new scheme. The
   scheme documented in build.gradle claimed the patch number was the count of
   passing tests. It had not been since 1.4.0, and it had never matched the real
   counts either (see the 1.1.143 note above). It is now plain
   MAJOR.MINOR.PATCH, with the patch a release counter within the minor line

 - versionCode is derived from versionName in the build script rather than typed
   alongside it, so the two cannot disagree. The encoding is unchanged --
   major*1000000 + minor*1000 + patch -- so no published versionCode moves

 - added a verifyVersionCode task that fails unless the declared versionCode is
   strictly greater than the highest published v* tag. Until now nothing checked
   this at all: the rule was stated in a comment and enforced by hand. The
   Jenkinsfile runs it before the release build, and its Checkout stage now
   fails if the tags were not fetched, since the task cannot compare anything
   without them

 - the test suite is Kotlin, which finishes the 1.4.5 migration: there is no
   Java source left anywhere in the repository. The 11 test files moved from
   src/test/java and src/androidTest/java to the kotlin/ directories beside
   them, which needed no build change -- AGP and the Kotlin plugin register
   src/<sourceSet>/kotlin themselves

 - the conversion was not a transliteration, and it turned up one real bug.
   GameRoundLoopTest asserted that every card in the deck was in a hand, a
   draw pile or the discard pile. Written the Java way it reads as

       val accounted = inHands
               + game.getDrawPile()!!.getNumCards()
               + game.getDiscardPile()!!.getNumCards()

   but Kotlin reads a line-leading + as unary plus and ends the declaration
   there: accounted was inHands alone, so the assertion compared one pile
   against the whole deck. It compiled without a warning. Java has no such
   reading, so the same text meant something else in the file it came from.
   The counts are now named and summed on one line

 - where nullability actually bit was not where the issue predicted. Hand(null)
   compiled unchanged everywhere, as expected. CardPile.getCard,
   Hand.getCard, Hand.getLowestCard and CardDeck.getCard are all nullable, so
   the reads inside loops needed !!, and each one now carries a comment saying
   why the read is safe instead of a bare !!. JsonRoundTripTest documents that
   the seat-index round trip is what makes Hand(null) legal, so tightening Hand
   breaks one assertion rather than forty call sites

- the reflection helpers in HandPlayabilityTest and GameRoundLoopTest now say
   out loud that f.set bypasses Kotlin's intrinsic null checks, which is why
   the AssertionError on a renamed field is the only guard there is

 - BUG FIX. The green 3 infection was charged again in every round after the
   one it was picked up in, and the running total grew by the whole accumulated
   penalty each time. A player who picked up a green 3 in round 1 paid 10 again
   in round 2 with no green 3 in sight, 20 again in round 3, and so on for the
   rest of the game

   Hand.calculateValue accumulating 10 per green 3 on a final score is correct
   and is untouched -- two cards, two infections. The compounding was one level
   up: Game.calculateScore adds the player's whole getVirusPenalty() to their
   round total, and nothing cleared that field between rounds. Only
   Player.resetGame() did, and that runs once per game. resetRound() now clears
   it, which is the round boundary and where the field's other round-scoped
   state already resets

   The winner was exempt from the charge, which was the one hint this was not
   meant to compound. That exemption is left as it is -- it is a separate rule

 - GameRoundLoopTest now pins the charge against the hand it should have come
   from: after a round, lastVirusPenalty must be exactly 10 per green 3 in that
   hand, for everyone but the winner and anyone holding all four bastard cards.
   The check runs on the random deal, which is not enough on its own -- on a
   deal with no green 3 in it the bug never fires -- so two further tests set
   the field by hand and drive two rounds around it

 - test count is 142 unit plus 9 instrumented. The two Hand-level tests that
   cover the accumulation, theVirusPenaltyAccumulates and
   theAidsCardInfectsOnlyOnTheFinalScore, both pass and both stay passing: the
   bug was never on that side
      


Version 1.4.8                2026-10-02

 - a malformed save is now rejected at the point it is read, rather than
   crashing some way into play. Game's resuming constructor caught JSONException
   and did nothing with it, so a well-formed JSON object missing any one key
   returned a Game that had stopped part-way through the parse: m_penalty and
   m_currCard were still null, and the crash came later, on the first card
   played, off one of the 68 m_penalty!! sites in Game.kt. Nothing in the stack
   trace pointed at the save file, because by then the save file was not in it.
   The catch logs and rethrows, so GameActivity's existing "if (m_game == null)"
   fallback starts a new game -- which is what the comment there already claimed
   happened, and which was dead code for as long as the catch swallowed the
   exception. Fixes issue #2

 - the log line is the point as much as the throw is. org.json names the key it
   could not find, so "Could not resume the saved game: No value for penalty" is
   the difference between a discarded save that is a mystery and one a bug
   report can be made from. The player still gets a new game either way; a
   discarded save is otherwise silent data loss

 - the m_penalty comment above the field said the resuming constructor left it
   null on a malformed save and pointed at issue #2. It now says what is true,
   which is that the plain constructor is the only path that leaves it null, and
   that is the NullPointerException the Java threw before startRound()

 - new MalformedSaveTest, 6 tests. It removes each of the 6 top-level keys, each
   of the 7 inside "state" and each of the 6 inside a player, and asserts every
   one is rejected -- the empty catch treated all of them identically, so testing
   one would not have covered the rest. Two of the cases are worth their own
   test: a save with no "players" key fails before anything is built, while a
   player missing "totalScore" fails only after the deck, both piles and all
   four seats have been constructed with wires running back to this Game, so it
   got the furthest before throwing

 - the good path is pinned too. aCompleteSaveStillResumes builds a save the app
   could have written -- a deck, a two-card draw pile, four hands of two cards
   each -- and asserts the cards came back, the dealer and current player exist,
   and seat 0's right-hand opponent is seat 1. Without it a fix that rejected
   every save would pass the other five tests

 - the player is now told. A discarded save was previously invisible from the
   table: the new game looks exactly like a resumed one, so their saved game
   disappeared with no sign it had ever been there. A Toast says so before play
   starts, LENGTH_LONG because the default is short enough to miss while the
   table is being laid out. A Toast rather than a dialog on purpose -- a modal
   would have to be dismissed before play, to say the one thing there is no
   action available for

 - the unreadable save is dropped rather than left for the next launch to fail
   on again. onPause writes a fresh snapshot, but only once this activity has
   been paused, and until then Main.onResume keeps offering "Continue" for a
   string known to be unreadable -- so a player who backs out and comes straight
   back in gets the same failure and the same toast with nothing new to show for
   it. Clearing the preference is the point at which we know it cannot be read

 - five more tests, on what the player sees rather than on what the constructor
   does. Four of them drive the real GameActivity.onCreate -- the constructor
   tests cannot reach the toast or the preference, because onCreate is where both
   live. anUnreadableSaveFallsBackToANewGame asserts getDeck() is null, which is
   the plain constructor's state and therefore says the fallback was taken; a
   resumed game has a deck even when the rest of the parse failed. It does not
   assert the absence of a crash, because the game thread is not running and
   checkCard is never reached -- the absence would have passed either way

 - aGoodSaveIsResumedAndKept is the control for all four: a good save is still
   resumed and still in preferences, so a fix that cleared "gamestate"
   unconditionally would fail it

 - test count is 153 unit plus 9 instrumented


Version 1.4.9                2026-10-02

 - penalty messages now name the player who has to act, not the one who threw the
   card. They read "North threw a Draw Four - 4 to South...", which asks a player
   mid-turn to work out who owes what from the back half of the sentence. They now
   read "South draws 4 cards (Draw Four from North)...". All eleven msg_penalty_*
   strings, not the ten with a count: the eleventh is Mystery Draw onto a
   non-number, which says so now -- "South draws nothing (Mystery Draw on a
   non-number)". The old wording described the thrower and never said the victim
   was fine. Fixes #3

 - the first and stacked variants stay separate, because they say different things
   about the same numbers. Penalty.addCards overwrites the generating player on
   every call, so on a stack the name is whoever stacked rather than whoever
   started it: "South draws 8 cards (Draw Four stacked by North)". That is why the
   stacked wording says "stacked by" and not "from". Whoever threw the first card
   is not recoverable once a second lands on it -- nothing on Penalty still holds
   it, including m_origCard, which is overwritten on the same call

 - the card counts moved out of bare literals at the six addCards call sites in
   Game.handleSpecialCards into Penalty.COUNT_DRAWFOUR and friends, alongside the
   PENTYPE_* constants. Nothing tied those six numbers to what the player was told,
   so a count could change in one place and not the other; and the counts are now
   read back off the penalty for the message, so the number shown is the running
   total by construction rather than by agreement. Not on Card deliberately: the
   same Draw Four costs 4 as a penalty and 50 points as a hand, and both are true

 - the five penalty branches were five copies of the same four lines -- add, test
   for a stack, pick between two resources, format three arguments -- differing
   only in the card's worth and its two strings. That is one function now,
   addCardPenalty. The Delayed Blast branch is why it takes the thrower as an
   argument: it advances the turn before adding, so its generator is not the player
   on turn

 - first-or-stacked is now read from the penalty's count before the add. The four
   fixed cards tested afterwards, as getNumCards() > 4 and so on, which is only
   equivalent because each adds exactly its own worth every time; Mystery Draw is
   worth whatever number it covers, so it already had to do it this way and is the
   reason the other four can now

 - new PenaltyMessageTest, 8 tests. Every message is formatted from the resource
   rather than written out again, so editing strings.xml -- the whole change here --
   is what the tests see; a test holding the sentences would have passed anyway.
   The argument specifiers are checked against the raw template as well as by
   formatting, because String.format ignores surplus arguments silently and would
   let a stray %4$s through to throw on a penalty card in front of a player

 - test count is 161 unit plus 9 instrumented

Version 1.4.13               2026-10-02

 - novice mode: pause after each play and wait for a tap instead of a timed
   delay, so a beginner can follow the game rather than race it. Off by default,
   beside game_speed in the settings. Fixes #5, the last open item of the
   Java-to-Kotlin migration's stage 7

 - it is a checkbox rather than another value on game_speed. game_speed is a
   number of milliseconds and two readers want exactly that -- waitABit, and
   GameTable's toast duration -- so a "tap to advance" value would have to be
   special-cased in both and the toast would get a made-up duration out of it.
   The choice between the two kinds of pause is the checkbox

 - the branch is in waitABit, not at each call site. The timed pause reaches
   play from everywhere: every promptUser that waits, and four deliberate
   think-pauses in ComputerPlayer. One branch means all of them follow,
   including the pauses between two computer players, which is what following
   the game actually means

 - Very fast still wins. getDelay() of 0 returns before the tap wait, so the
   one setting whose purpose is not to wait is not turned into a setting that
   does. That ordering is a test

 - the tap does not go through drawPileTapped, and must not. That method clears
   the round-start wait and then, if the player is human, calls
   turnDecisionDrawCard -- so reusing it would hand the player a draw decision
   they never made, on a turn that has not started. There is a separate
   Game.tableTapped with no side effect beyond the wait, called from
   GameTable.onTouchEvent before the pile and hand handling so the same touch
   can do both things

 - a wait that can wait for ever is a shutdown hazard, and this one could. It is
   a spin of Thread.sleep(100) on the game thread, so backgrounding the app
   mid-pause would leave it sitting there. Two exits, both tested by releasing a
   wait that is provably already blocked: pause() clears the flag, which is the
   ordinary case, and the loop checks m_stopping, which covers the rest.
   Resuming does not demand a tap for a pause the player never saw the end of

 - new NoviceModeTest, 11 tests. The waits run on a background thread, because
   blocking is the behaviour, and each one waits for waitingToAdvance() before
   asserting it is still blocked, so no test can pass by the wait never having
   started. Disabling the waitABit branch fails 5 of the 11

 - one test was wrong on the first pass and the correction is the useful part:
   it asserted that a draw-pile tap releases a novice wait, which it does not --
   the app calls tableTapped first and then the pile handling. Split into what
   actually holds: a draw-pile tap alone does not release it, and the two calls
   in the order onTouchEvent makes them both release and decide the draw

 - test count is 182 unit plus 9 instrumented


Version 1.4.14               2026-10-02

 - Expert AI, issue #6: hoard wilds, count what the opponents are holding, and
   lead a colour chosen against the table rather than against itself. The last of
   the original author's stage-7 items

 - a wild scores -60 for Strong and above. That is below the worst any other card
   can reach -- the Magic 5 is -5, the MAD card can be -20 -- so a wild goes out
   when the hand is otherwise stuck and stays in hand otherwise, and above the
   -1000 that maxpointval starts at, so a hand of wilds still plays one rather
   than drawing. The Java had "if (wild_count < opponent_card_count - 1) testval
   = 0" with testval already 0 from its initialiser, so both arms assigned 0 and
   the condition chose nothing. Hoarding is what the condition was reaching for.
   wild_count went with it: nothing tests it any more

 - one exception to the hoard, and it is the reason the old condition mentioned
   the opponents' card count at all: an opponent on their last card. A wild is
   the only card in the deck that changes the colour at will, so it is the only
   way to stop somebody who is about to go out from simply following the lead

 - the Mystery wild now falls out of its own ladder onto the hoard score when it
   has no opinion. Its comment already said to keep it off non-numbered cards; a
   wild on a wild used to score 0 and win a tie against any other worthless card.
   The sentence is now the code

 - sub-item 2: countUnaccountedInColor works out what each opponent might hold
   from the deck, this seat's hand, and the discard pile. It deliberately does not
   ask the deck which hand a card is in, because the deck holds references to the
   same Card objects the hands do and counting them would be a sharper answer
   than a player at the table could have

 - sub-item 3: chooseColor's "FIXME -- we need a real strategy" is answered. The
   colour a seat holds most of is half a strategy -- it maximises what the seat
   can follow its own lead with, and it is all a player watching would see the
   Expert doing wrong, since it leads the colour the whole table can already
   match. Expert still counts, and still prefers the colour it can keep playing,
   but a colour the opponents are likely to hold is now charged for, and a colour
   the seat holds nothing of is never named

 - the charge is a probability over cards the table cannot account for, with the
   draw pile's share discounted by how much of it the pile could hold. That is
   what makes it tighten as the round runs and stay quiet while the deck is
   mostly unknown: at the top of a round the draw pile holds nearly everything
   nobody can see, so "this opponent is probably holding red" is not yet worth
   changing a play for. Each opponent is weighted 4/(cards+1), so a player on
   their last card costs more than one with a full hand

 - two bugs found while writing the tests, both in the new code. The draw-pile
   discount was missing its / pool, so it saturated for any draw pile small
   enough to matter and read "certain" from the first turn of a round. And a
   pigeonhole shortcut I added for opponents holding more cards than there are
   other colours turned out to be redundant: the product's own zero factor
   already reaches 1.0 there, checked over every pool, inHands and numCards up to
   60, so the shortcut went back out

 - sub-item 3 also wanted the colour balance to *choose* a lead rather than just
   score one. Two cards of equal score are now decided by the play that leaves
   the hand most even, so which of two identical cards gets played is no longer
   the order of the hand array. Skill 0 and 1 keep >= and the last card wins --
   arbitrary, but the behaviour they have always had

 - the isFinite check in that tie-break is doing real work.
   computeChangeInColorBalance divides by the balance before the play, and a hand
   with one card of each colour has a balance of exactly 0, so the result is an
   infinity rather than a number. Unguarded, comparisons against it would either
   drop every candidate or favour whichever card was scanned first, for no
   reason. AnEvenHandFallsBackToHandOrder pins that

 - the other three TODO comments in playCard are still there: throwing the mystery
   draw on numbered cards, MAD when the hand's points are too high, and offensive
   cards against players on low card counts. The first two are done and the
   third is now half done by the colour pressure, but they are the author's
   notes and rewriting them as if they were a specification would be a claim
   about work nobody has done

 - AiStrategyTest, 21 tests, 203 unit. The suite had nothing that could see which
   card the AI picks -- HandPlayabilityTest covers legality and
   GameRoundLoopTest asserts invariants, never decisions -- so every one of these
   is a decision a plausible-looking edit would change. The fixture is a real
   round off the real 216-card deck, because calculateValue is what supplies the
   point values the MAD and Draw Four scores are read from

 - each of the eight behaviours was checked by breaking it on purpose and
   confirming something fails. That found two tests that pinned nothing: a "the
   Expert holds a wild" test that a wild scoring 0 would also have passed, and a
   pigeonhole test that passed with the whole colour strategy switched off. The
   first is now merged into a test that says plainly it is the weak version, and
   the second is gone
