# Card faces as SVG

85 files in `svg/`: 84 card faces plus `card_back.svg`. Generated by
`generate_card_svgs.py`, which parses the card table out of the Kotlin so the set
cannot drift from the app.

    python3 artwork/cards/generate_card_svgs.py

**These are not a vectorisation of the existing art, and they are not a drop-in
replacement for it.** Read this section before using any of it.

## What is measured, and therefore faithful

Geometry and palette were read out of the bitmaps in
`com.smccloud.hotdeath/app/src/main/res/drawable-xlarge-hdpi` rather than guessed.
The PNGs are 8-bit indexed, which the standard library can decode, so the numbers
below came out of the actual pixels.

**The card is 103 × 160**, matching that bucket exactly.

**The pale panel is at x 17, y 31, 66 × 96.** Found by taking the largest pale
connected component on each card, and it lands on the same box every time — 66
wide, 96 tall, on every card measured.

**The suit colours**, as the mean of the frame interior over a clean patch at
x 3..15, y 60..110, which avoids both the antialiased card edge and the corner
glyphs. Each was consistent to within one quantisation step across every card
sampled:

| Suit | Frame |
|---|---|
| Red | `#C70E26` |
| Green | `#028139` |
| Blue | `#044FA1` |
| Yellow | `#E6880B` |
| Wild / back ground | `#262529` |
| Panel bone | `#DCDBD6` |

**The card set itself**: 81 IDs in `Card.kt`, 84 drawables in
`GameTable.initCards()`, because three cards carry a family-friendly spelling as
well as an original one (`card_green_3_aids_ff`, `card_blue_0_fuckyou_ff`,
`card_yellow_0_shitter_ff`). The generator asserts that no declared ID is missing
from the table and writes exactly the 84, so adding a card without art fails
rather than silently producing a set of 84 that is one short.

## What is substituted

**Letterforms.** The original uses a display face for the big glyphs and a
blackletter for the special card names — "HOLY DEFENDER" on the red 0 is set in
gothic. Neither font is in the repo, and neither can be recovered from a 103 × 160
raster. Everything here is set in a generic sans stack, so the glyph *shapes* will
not match. The original's numerals have a distinctly heavy, slightly flared look
that a generic bold sans does not reproduce.

**Motifs** are geometric stand-ins, not traces: the crown on the Holy Defender is
a polygon, the MAD bullseye is two circles, the wild wheel is four pie wedges, the
Spreader and Skip arrows are triangles. Each is recognisably *the same idea* at the
right place and roughly the right size. None is the original shape.

**The back's logo** is a red rounded square with "HDU" in gold on a diagonal,
because that is what is legible at 103 × 160. If the real mark is a stylised
hot-death symbol, this is a placeholder.

**Label placement** was read off the reference bitmaps by eye and is the weakest
part. Word positions are in `WORD_Y` and the per-card `word_slot`, and no label has
been confirmed to sit where the original puts it.

## What has not been verified at all

**Nothing here has been rendered.** There is no SVG rasteriser on this machine —
no `rsvg-convert`, no Inkscape, no ImageMagick, no `cairosvg`, no Pillow — so
every claim above is about structure and colour, and **not one of these files has
been looked at**. What was checked: all 85 parse as XML; all declare
`viewBox="0 0 103 160"`; every face carries the measured panel box and a frame
colour drawn from the sampled set; the file set matches `initCards()` exactly in
both directions with no orphans, the only PNG without an SVG being `card_badge`,
which is not a card face.

Rendering them is the first thing to do with them.

## The 69 discrepancy

`card_yellow_69.png` shows a big **6**, not a 69 — `CardDeck` gives that card
`VAL_`-style value 6, and the original art appears to have been drawn from the
value rather than the name. `Card.toString` calls it 69, the README calls it 69,
and it locks a hand total to 69.

These SVGs print **69**. That is a deliberate departure from the bitmap, on the
grounds that the card's identity is 69 and the bitmap is an artefact of how it was
drawn. Worth confirming, because if the face really is meant to read 6 then this is
the one place the set knowingly differs from the art it was generated from.

## If these get used

Android cannot consume SVG directly — `BitmapFactory.decodeResource` will not read
one, and `res/drawable` has no SVG support. So these are either **masters to
rasterise** per density bucket at build time, or they need converting to
`androidx.vectordrawable` XML. Either way that is a build step this repository does
not currently have, and it is the reason the three-ratio problem in issue #9 is
worth solving at the generator rather than in the art.

`card_badge` has no SVG here. It is drawn on top of a hand rather than being a card
face, and it is 40 × 40 rather than the card's aspect ratio.
